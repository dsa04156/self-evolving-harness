DECISION: REVISE

NOVELTY:
On the packet’s own evidence, the remaining gap is distinct enough to justify a bounded prototype, but only as a systems integration and enforcement contribution. The defensible contribution is not trace-driven mutation, worktrees, held-out evaluation, prompt evolution, or a generic self-improving agent. It is the combination of a standalone runtime, typed and content-addressed harness composition, explicit separation between task execution and evolution, machine-enforced principal boundaries, and evidence-linked promotion. That contribution collapses if any of those properties exist only as conventions, prompts, directory layouts, or architectural diagrams. The prior-art summary is adequate for this gate only because its absence claims are explicitly scoped; later novelty claims will require the referenced inspection ledger.

CORRECTNESS:
The task-execution versus harness-evolution distinction is conceptually clear, but the current object model cannot yet enforce it correctly. A content-addressed `HarnessVersion` cannot contain mutable evaluation references, promotion decisions, or state history without changing identity after creation. The same problem applies to component `evaluationHistory`. Those records must be external append-only objects referencing an immutable manifest hash. Activation must atomically select an entire evaluated `HarnessVersion`, not independently project active component versions. Persistent memory contents, workspace state, resumable jobs, and descendant subagents are behaviorally significant but are not currently pinned or reset by the version contract. Finally, `Skill` and `WorkflowPolicy` remain potential containers for arbitrary executable code, making the stated mutation boundary nominal rather than real.

EVALUATION FAIRNESS:
The budget philosophy is strong, but the executable evaluation contract is not yet fair or internally consistent. H1 changes attribution, mutation scope, and possibly edit size simultaneously, so it cannot identify the effect of attribution. B5’s size-matched control must be mandatory, and a bounded attribution-ablated control is also required. `K=5` is not operationally defined. Track A and Track B do not specify exactly which methods see task feedback, which phase consumes the evolution budget, or which comparisons support which claims. Gate-query adaptivity is unbounded. More seriously, the “sealed multi-cause” set appears as a candidate gate even though sealed test data is declared unavailable for promotion. Metrics are not explicitly mapped to mine, gate, and final-test splits. Public Terminal-Bench IDs can be withheld from mounts, but they cannot honestly be treated as unknown sealed data, especially with possible model pretraining contamination.

GENERALIZATION:
H2 is appropriately centered on a frozen artifact and no-retry held-out pass@1, and the temporal holdout is the strongest proposed generalization evidence. It is not yet protected against benchmark-author bias, however. Temporal tasks need independent or blinded authorship, predeclared inclusion criteria, immutable timestamps and hashes, and no author access to candidate results. H4 is acceptable only as a secondary stretch claim with the second model selected and frozen before transfer results are observed. A failure of H4 should remain isolated from the architectural claim, as the packet already states.

REPRODUCIBILITY:
The proposed manifests, event receipts, budget ledger, content hashes, exact revisions, and protocol versioning are a good basis. Reproducibility still requires one canonical serialization and hashing algorithm, explicit dependency-closure hashing, normalized file and text handling, exact protocol schemas and error semantics, immutable environment and toolchain digests, and a reproducibility tier for provider models whose weights cannot be identified. The proposed pooled task×seed bootstrap risks treating repeated seeds of the same task as independent observations. Statistical units, resampling hierarchy, primary estimands, candidate-selection multiplicity, and seed-count determination must be frozen before confirmatory evaluation.

SECURITY:
The target principal separation is directionally correct, but it is not yet a security contract. Different implementation languages do not prevent evaluator impersonation; they merely reduce accidental shared-code coupling, a modest engineering benefit humans occasionally mistake for a security boundary. Enforcement must come from separate identities, authenticated protocol messages, immutable executable and policy digests, mount and capability restrictions, provider-only network egress, principal-scoped credentials, host-enforced budgets, fresh sandboxes, and independent result verification. The threat model must also state whether the host, model provider, audit-store operator, and benchmark author are trusted. Hash chains provide tamper evidence under stated trust assumptions; they do not make a locally controlled filesystem intrinsically immutable.

CLAIM DISCIPLINE:
The packet is appropriately conservative about general self-improvement, negative results, transfer failure, and the difference between recovery and evolution. Keep that discipline. Do not call the public Terminal-Bench split “sealed” without qualification, do not describe the audit plane as tamper-proof, and do not attribute lower regression to attribution unless the mutation-boundary and edit-size confounds are controlled. Gate 1 may support an architectural feasibility claim only. Performance, security, autonomous improvement, and cross-model generalization remain unauthorized.

BLOCKING FINDINGS:

1. `HarnessVersion` and `HarnessComponent` mix immutable content-addressed identity with mutable evaluation history, decisions, lifecycle state, and registry projection. That makes version identity unstable or circular.
2. The mutation model does not prevent `Skill`, `WorkflowPolicy`, prompts, references, generated artifacts, or dependency changes from carrying arbitrary executable behavior outside the nominal one-component or 8 KiB limit.
3. Persistent memory contents, workspace state, recovery checkpoints, subagents, and backend jobs can alter behavior while retaining the same `HarnessVersion`; evaluation reset and inheritance semantics are unspecified.
4. Candidate gates appear to consume sealed multi-cause test cases, contradicting the rule that test data is unlocked only once after final freeze. Attribution and performance metrics are not mapped unambiguously to specific splits.
5. H1 is causally confounded. B5 changes more than attribution, its size-matched control is merely proposed, and there is no bounded attribution-ablated baseline.
6. Matched-budget accounting lists many caps but does not define the phase ledger, primary equality rule, `K`, unused-budget handling, provider-side accounting, static-baseline treatment, or evolution-cost amortization.
7. H3 can report “efficiency” by moving tokens from the proposer to a summarizer or attribution model. Its current proposer-token metric does not measure total system inference cost.
8. The confirmatory statistics are under-specified. Two named seeds are not a power or precision plan, pooled task×seed resampling may create pseudo-replication, and multiplicity from candidate selection and multiple baseline comparisons is untreated.
9. HarnessFaultBench freezes IDs and categories but not executable fixture semantics, generation rules, difficulty balance, oracle construction, or scorer behavior. Implementing fixtures after architectural decisions leaves material room for benchmark tailoring.
10. Public Terminal-Bench tasks are withheld during execution, not demonstrably sealed from model pretraining or prior exposure. The current terminology overstates leakage resistance.
11. The trust plane lacks a principal-by-capability enforcement matrix, authentication contract, provider-egress policy, trusted-computing-base statement, and precise audit threat model.
12. ADR-0001 incorrectly treats the Node/Python language split as preventing evaluator impersonation. JSON Lines framing, authentication, correlation, size limits, timeout behavior, artifact transport, and crash semantics are also unspecified.

REQUIRED REVISIONS:

1. Split each content-addressed object into an immutable manifest and external append-only lifecycle records. The `HarnessVersionId` must hash only immutable composition and policy inputs. Evaluations, decisions, state transitions, canary records, and activation history must reference that ID without modifying it.
2. Replace per-component active projections with one atomic deployment or channel pointer to an evaluated whole-harness manifest. A component composition that was not evaluated together must never become active through independent registry updates.
3. Define canonical serialization, encoding, normalization, dependency ordering, symlink handling, referenced-artifact treatment, and hash recomputation. Every component hash or version closure must cover all transitive behavior-bearing dependencies.
4. Make mutable class and component type authoritative properties of the immutable type registry, not candidate-supplied assertions. Provenance and attribution receipts must be emitted by trusted planes rather than self-declared inside candidate payloads.
5. Specify allowed payload languages for every mutable type. For the MVP, either make `Skill` and `WorkflowPolicy` declarative and non-executable, or define a capability-limited DSL. Ban candidate-controlled imports, build hooks, tool registration, middleware, dynamic downloads, compressed or encoded payload expansion, external file indirection, and unbounded code generation.
6. Measure mutation size over the fully expanded canonical dependency closure. Retain 8 KiB only as a defense-in-depth ceiling, not as evidence of scientific matching. Also record semantic capability changes and normalized token or AST-level edit size where applicable.
7. Provisionally retain the one-component and explicit two-component limits for the MVP, but count all transitively changed dependencies. A proposal that modifies one manifest while replacing multiple referenced artifacts is a multi-component change and must be rejected.
8. Define runtime-state reproducibility. Evaluation must start from declared memory, filesystem, environment, checkpoint, and cache snapshots. Descendant subagents and background jobs must inherit the initiating session’s harness ID, split permissions, principal, model identity, and budget; they may not rebind to a newly active version.
9. Publish a metric-to-split matrix. No `D_test` or sealed-test metric may participate in candidate creation, selection, promotion, threshold tuning, or rollback policy. Move multi-cause recall to final confirmatory reporting or create a separate multi-cause `D_gate` split before protocol freeze.
10. Bound gate adaptation. Freeze the maximum candidate count, gate evaluations, released aggregate fields, and whether gate results are visible to the proposer. Prefer a mine-only generated candidate batch followed by one non-adaptive gate selection. Every released gate result must count as a feedback event.
11. Rename the Terminal-Bench split as a “withheld public test” or equivalent. Record model-contamination risk explicitly. Reserve “sealed” for data that was genuinely unavailable to the proposer, runtime developers, and model-selection process.
12. Add a temporal-holdout governance contract: independent or blinded task authors, predeclared task inclusion and rejection rules, timestamped content hashes, frozen verifier construction, no access to candidate outcomes, and a documented contamination check.
13. Make B5’s size-matched control mandatory. Match model, proposer, feedback, candidate count, component count where possible, transitive edit size, and evaluation budget. Add a bounded attribution-ablated baseline that uses the same mutation surface and proposal budget as B6 but does not receive attribution output.
14. Define `K` and provide separate protocols for Track A and Track B. State exactly what data and feedback each baseline receives, which phase each budget covers, whether unused resources can be reallocated, and which track supports H1, H2, H3, or scaling claims.
15. Separate evolution cost from final test-time cost. Static B0 may remain a performance anchor, but it cannot be described as receiving an equal development budget. Report total evolution cost, final per-task inference cost, and any amortization or break-even analysis separately.
16. Freeze a phase-specific budget ledger for mining, summarization, attribution, proposal, gate selection, final solving, and background work. Charge failed, cancelled, cached, hidden-reasoning, subagent, judge, and retry calls according to one declared provider-accounting rule. Deterministic verifier compute should be reported separately rather than silently converted into model tokens.
17. Revise H3 to use total charged inference tokens or provider cost, including summarization, attribution, judging, and proposal generation, as the primary efficiency measure. Proposer-context tokens may remain secondary. The 20% margin is acceptable only as a predeclared material-effect threshold on the total charged measure with an interval estimate, not as a proposer-only point estimate.
18. Do not accept the −5 percentage-point attribution margin or −2-point candidate-quality margin merely because they are written down. Justify them using pilot variance and task resolution on mine-only or dedicated pilot data, then freeze them before any gate or test observation. Zero new safety violations remains an acceptable hard constraint.
19. Predeclare the primary estimands and comparison hierarchy. Use task-clustered or hierarchical paired resampling with seeds nested within tasks, determine the confirmatory seed count from a frozen precision or power rule, and address multiplicity across candidates, hypotheses, and baseline comparisons.
20. Define the candidate cost gate precisely. Identify the cost vector or scalar, the baseline denominator, how a greater-than-10% increase is computed, and the minimum success improvement required. “Pareto improvement” cannot remain an informal escape hatch.
21. Freeze HarnessFaultBench’s fixture-construction contract before implementing fixtures: input template, injected-fault mechanics, oracle, expected attribution labels, ambiguity policy, difficulty balancing, deterministic scorer, multi-cause labeling, and independent review. IDs and category names alone are not a frozen benchmark.
22. Add a principal-by-capability matrix covering runtime, operations owner, proposer, evaluator, promoter, audit store, model-provider proxy, and benchmark author. Include UID/container identity, readable and writable mounts, permitted message types, secrets, network destinations, resource caps, and authority to create or validate each record.
23. Define immutability as protocol-scoped digest pinning. Changes to evaluator, permissions, budgets, model configuration, trace collector, audit verifier, promotion policy, or benchmark material must create a new protocol version and cannot be mixed into confirmatory evidence from the previous version.
24. Revise ADR-0001. The Node.js/TypeScript runtime, Python evaluator, JSON-schema boundary, append logs, rebuildable SQLite projection, and Git lineage are acceptable engineering choices. Remove the claim that language separation prevents impersonation. Require OS-level separation, authenticated and schema-validated messages, correlation IDs, protocol versions, payload-size limits, timeouts, error states, artifact-by-hash transport, and locked toolchain and environment digests.
25. Remove the pre-contract Python spike from every runtime, package, test, import, and evidence path before implementation. It may be preserved only as a hash-pinned artifact under an explicit `spikes/` or archival location with a non-authoritative notice. No runtime implementation may inherit behavior merely by importing or copying the spike without mapping it back to an approved contract.
26. Resubmit Gate 1 with the revised manifests, state invariants, split matrix, baseline matrix, budget ledger, statistical plan, principal matrix, fixture specification, ADR, and explicit validator/adversarial-test acceptance criteria.

NON-BLOCKING RECOMMENDATIONS:

1. Add a claim matrix mapping each hypothesis to its dataset, permitted feedback, baselines, estimand, statistical test, falsification condition, and maximum authorized wording.
2. Define the MVP canary as an offline replay or isolated synthetic canary. Do not introduce live users, production repositories, or confirmatory test tasks merely because the state machine contains a box labeled `canary`.
3. Treat Git commits and worktrees as lineage conveniences only. The content-addressed manifest and trusted audit receipts should remain authoritative when Git metadata disagrees.
4. Replace `observed_fact` with `recorded_observation` or attach a producer-trust level. A runtime event can be faithfully recorded while still originating from a compromised tool or untrusted process.
5. Preserve all rejected candidates, invalid proposals, safety failures, and budget-exhausted runs with protocol and environment hashes. Negative-result retention is unusually sensible here and should survive contact with publication incentives.

AUTHORIZED NEXT SCOPE:
Revise the research contract and design artifacts only. Authorized work is limited to immutable manifest and lifecycle-record schemas, component payload restrictions, state and activation invariants, split and feedback rules, baseline definitions, the budget and statistical protocol, the principal-capability matrix, the HarnessFaultBench fixture specification, ADR-0001 revision, validator acceptance criteria, adversarial-test planning, and quarantine of the Python spike. Runtime-kernel implementation, evolution-loop implementation, provider calls, benchmark execution, `D_gate` or `D_test` access, canary operation, promotion, and performance or security claims are not authorized until the revised Gate 1 packet is approved.
