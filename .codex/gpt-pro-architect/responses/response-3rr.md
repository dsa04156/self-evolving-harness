SEMANTIC_EXECUTION:
The semantic development-fixture blocker is closed.

The reported replacement no longer determines success by reading the target component, manifest role, good/fault pairing, expected result, or scorer label. The selected harness is instantiated through the standalone runtime, and the eight mutable component types affect actual runtime decision points:

SystemPrompt changes model instructions;

ContextPolicy changes selected context and visible tools;

MemoryRetrievalPolicy changes retrieved memory and ordering;

Skill changes injected guidance and completion conditions;

WorkflowPolicy changes closed transitions and dispatched actions;

RoutingPolicy changes execution routing;

SubagentPrompt changes a launched descendant’s context;

ToolDescription changes the model-visible catalog without changing the immutable implementation or schema.

The fake provider is keyed by the canonical projection of the actual model request, the tools consume validated calls through immutable implementations, and the verifier inspects observable text and workspace outcomes rather than harness identity. The packet also reports pre-verifier behavioral divergence for all 28 cases.

The known-good request-table construction is acceptable for a semantic wiring fixture. It deliberately makes deviations from known-good requests detectable and therefore does not establish realistic model behavior, fixture difficulty, or attribution identifiability. It does, however, satisfy the narrower requirement that component payload semantics, rather than manifest labels, causally drive execution.

The terms “semantically executable development fixture” and “semantic wiring fixture” are now acceptable. The terms “research-valid attribution benchmark,” “attribution-ready corpus,” or equivalent remain unsupported.

AUTHORITY_AND_LEAKAGE_BOUNDARY:
The execution/oracle separation is sufficient for visible deterministic development.

The runtime, provider, tools, verifier, attribution adapter, and proposer-facing package receive no ground-truth component, mechanism, pair mapping, expected outcome, patch, or oracle object. The executor necessarily receives a selected harness ID for registry resolution, but it receives no information describing that ID as good, faulty, or associated with a particular target.

The allowlist adapter is also sufficient to permit label-blind attribution development. It exports coarse behavioral observations while removing raw content, paths, hashes, opaque IDs, harness and component identities, provider metadata, mutation data, expected values, and oracle labels. The reported injected-label tests, opaque-ID-renaming invariance, corpus-order invariance, forbidden-import checks, and zero leaked forbidden values materially support that boundary.

This is not a sealed-data or hostile-principal boundary. Source-import scans and schema separation are development controls, not a substitute for a future independent benchmark-author principal and evaluator vault. They are sufficient here only because all 28 fixtures are visible development fixtures and no confirmatory claim is authorized.

For any newly authorized attribution run:

The attributor must consume only the committed label-blind projection.

Prediction records must be content-addressed and finalized before any scorer joins them with oracle labels.

The attributor, mutation proposer, candidate runtime, and candidate evaluator must never receive the oracle package.

Oracle access must remain confined to the development scorer and governance verifier.

Any iterative tuning on these 28 fixtures makes resulting scores development diagnostics, not held-out attribution evidence.
