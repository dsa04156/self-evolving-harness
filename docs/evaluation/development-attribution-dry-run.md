# Visible-fixture attribution and mutation dry run

## Status and claim boundary

This track is a deterministic development diagnostic over the 28 public,
visible `D_mine` semantic fixtures. It is not a research attribution result,
candidate-selection signal, promotion decision, benchmark pilot, or
self-improvement result.

The track is authorized only by the Architect 3RR decision and the signed
append-only remediation closure. It does not instantiate gate, final,
multi-cause, temporal-holdout, or Terminal-Bench task bodies. It does not call
a real provider.

## Authority sequence

1. The label-blind attributor reads only the committed corpus projection.
2. It emits one explicit status for every unique trace and every occurrence.
3. A proposer signs the complete prediction set before oracle access.
4. Only after that seal, a separate evaluator identity reconstructs the
   visible-fixture oracle and records a signed access event.
5. The scorer joins the oracle to the sealed predictions and emits diagnostic
   top-k counts, abstentions, failures, and confusion rows.
6. A bounded mutation proposer chooses a component type only from a committed
   top-1 prediction and changes one mutable component in a synthetic harness.
7. Operations immediately signs a non-promotable record for the candidate.
8. A separate Python process evaluates only synthetic task pairs with a fake
   provider contract and immutable tool contract.
9. A protocol-author signature quarantines the full artifact graph from every
   research, gate, canary, promotion, deployment, production-pointer, and claim
   use class.

The scorer can observe the public fixture oracle. The attributor, mutation
proposer, and external candidate evaluator cannot import or receive that
authority.

## Reproducibility

After committing the implementation, generate the content-addressed evidence
from a clean worktree:

```bash
npm run generate:development-attribution-dry-run
```

Verify the persisted bundle independently:

```bash
npm run verify:development-attribution-dry-run
```

The verifier:

- binds every implementation file to the evidence source commit and tree;
- deterministically replays label-blind predictions and their signed seal;
- reconstructs the public oracle only after the seal and replays scoring;
- reconstructs the synthetic parent, bounded mutation, and candidate identity;
- reruns the external Python evaluator and checks byte-equivalent results;
- verifies every schema, content hash, file hash, Ed25519 signature, and
  cross-reference;
- confirms all generated artifacts are covered by the quarantine;
- exercises every allowed and prohibited quarantine use class.

The generator refuses a dirty worktree or an existing output path. It never
overwrites prior evidence.

## Mechanically enforced exclusions

The development candidate cannot enter:

- the main HarnessVersion qualification lifecycle;
- research candidate selection;
- canary or approved states;
- deployment or a production pointer;
- a research protocol manifest.

Development diagnostic artifacts cannot be referenced by an attribution gate,
research threshold, promotion decision, claim table, or research evidence
record. These are runtime authorization checks, not documentation-only labels.

## Interpretation

Diagnostic top-k values are useful only for debugging the public fixture
pipeline. They must not be reported as benchmark accuracy, held-out
generalization, superiority over B0–B6, or evidence that the harness improves
itself. A future research protocol needs a separately approved Gate 3 packet,
frozen matched budgets, inaccessible held-out data, and a new authorization
decision.
